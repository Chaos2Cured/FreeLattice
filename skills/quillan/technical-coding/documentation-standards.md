# Documentation Standards

## Overview
Documentation standards define how software is documented to ensure clarity, consistency, and usefulness across the codebase. Good documentation serves as a force multiplier enabling faster onboarding, fewer bugs, and more confident changes. This sub-skill covers code documentation, API references, architecture decisions, and project documentation.

## Core Concepts
- **Code Documentation**: Docstrings/comments explaining why (not what) with type annotations for public APIs
- **API References**: Auto-generated or manually maintained documentation with examples and schemas
- **Architecture Decision Records (ADRs)**: Documents capturing significant architectural decisions and their rationale
- **Project Documentation**: README, setup guide, contribution guide, and onboarding documentation
- **Documentation as Code**: Treating docs like code with version control, reviews, and CI validation

## Application
Document why a decision was made, not just what was decided. Use ADRs for all significant architectural decisions. Keep documentation close to code (docstrings, README in repo). Review documentation as part of code review. Test documentation by asking a new team member to follow it.
