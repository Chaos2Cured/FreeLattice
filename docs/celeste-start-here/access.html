Access notes from one public probe

These notes record what a single anonymous fetch observed on 2026-11-07. They do not explain every report that an AI could not view FreeLattice. This edition does not change private pages, does not add a bypass, and does not ask a provider to allowlist the site.

  • GET https://freelattice.com/ , /for-ai.html , /robots.txt , /library/AUTONOMY.md , /beacon.json , and one existing PDF returned HTTP 200. A second GET of /for-ai.html with a GPTBot user-agent also returned HTTP 200 on this path.
  • Those responses showed server GitHub.com, via Fastly/varnish, Access-Control-Allow-Origin: *, Accept-Ranges: bytes, and no WWW-Authenticate challenge. No X-Robots-Tag header was present on the sampled responses. www.freelattice.com returned 301 to the apex host.
  • Observed content types on existing files: HTML as text/html, Markdown as text/markdown, JSON as application/json, PDF as application/pdf. This repository cannot set a different per-file header on GitHub Pages.
  • The site's own robots.txt already says Fastly may rate-limit some fetcher addresses and that the limit is outside the site's control. That sentence is the project's existing statement. This page does not treat it as the verified cause of any particular failure.
  • GitHub's robots.txt, fetched the same day, lists Disallow: /*/raw/ for named agents including GPTBot and ClaudeBot. A raw.githubusercontent.com copy is therefore a weak fallback for those agents. The same bytes on freelattice.com are the ordinary public HTTP copy. This repo cannot change GitHub's robots or an outside provider's allowlist.
  • The browser service worker is unchanged. A plain HTTP GET does not execute it.
  • Existing noindex pages were left as they were. robots.txt Allow rules were not narrowed.
