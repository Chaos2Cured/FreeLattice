======================================================================
WHY (THE AUDIT IN ONE SCREEN)
======================================================================
Kirk asked: "I thought we had encryption for FreeLattice using our phi-harmonic hashes?"
Plain answer: no phi-harmonic hash encrypts anything today. The phi pieces fingerprint, check, or name things. Real encryption exists in three places, none of them for chats, and none use phi:
  a. API keys and tokens (app.html "phi-Root Encryption", about line 25499): AES-GCM. The key comes from a random device key kept in localStorage (fl_device_encryption_key). There is no phi in the current derivation. The old derivation (provider + "1.6180339887" plus a fixed salt in the source) is still a decrypt fallback, and anyone with the source can recompute it. The v2.1 changelog text "phi-Salt Encryption, golden-ratio derivation" is no longer true.
  b. Soul file export: AES-GCM with PBKDF2 (100k) from a password you type. Real password encryption, for that file only.
  c. Desktop: the Ed25519 companion seed and the pair seed are encrypted at rest by Electron safeStorage (the OS keychain).
Chats themselves (IndexedDB FreeLatticeDB: messages and conversations, plus the Memory Index copy in FreeLatticeMemory) were plain text. That is what this brick fixes.

======================================================================
WHAT THIS BRICK DOES
======================================================================
1. FLChatVault (inline in app.html, right after phiHashData)
   - On first run it makes 32 random bytes (crypto.getRandomValues), imports them as a NON-EXTRACTABLE HKDF CryptoKey, and wipes the bytes. The CryptoKey is stored in a separate IndexedDB database "FreeLatticeVault" (store "keys"). Raw key bytes are never stored anywhere and can't be read back out by page code.
   - A random 32-byte salt is stored next to it.
   - HKDF-SHA-256 derives the AES-GCM 256 chat key. Label: "freelattice.chats.v1|phi=1.6180339887".
   - Before the key is trusted with a single chat, it's written, read back, and its key ID checked.
   - Each record gets a fresh 12-byte IV. Additional authenticated data (AAD) ties a message to its conversationId, role and timestamp, and a conversation to its id. So a sealed message moved or edited outside the app reads as "locked", not as wrong text.

2. Where phi is honest, and not decorative
   - Domain label: phi is in the HKDF labels. Chat keys can never collide with keys derived for any other purpose from the same root. This is real domain separation. Any unique string would do the same job, and the paste says so.
   - Key ID: a one-way 128-bit check value (HKDF with a second label) goes through phiHashData and is shown as "phi-xxxxxxxxxxxxxxxx". The vault uses it to tell the right key from a wrong or missing one before trying to open anything. It reveals nothing usable about the key.
   - Phi is never the secret and adds no strength. The strength is the 256 random bits.

3. What is sealed
   - FreeLatticeDB/messages: content
   - FreeLatticeDB/conversations: name, title, lastMessage, contextNote
   - FreeLatticeMemory/conversations (the Memory Index keeps a full second copy of every chat): title, messages, tags, summary, keywords
   Left readable on purpose (the app needs them to sort and find things): ids, conversationId, role, timestamps, counts. Say so plainly: the fact that a chat exists, and when, is still visible.

4. How it plugs in (smallest change)
   - The plain helpers dbGet / dbPut / dbGetAll / dbGetAllByIndex stay as written. Right after dbCount, wrappers seal on the way in and open on the way out. Every existing reader keeps working: switchToConversation, export, memory summary, GitHub sync, memory index sync.
   - The same pattern wraps miGet / miPut / miGetAll inside the MemoryIndex module.
   - Four places read IndexedDB directly and now open sealed records first:
       * FLSearch cross-store search (searchStore)
       * Soul file export (readDB of conversations)
       * Memory Vault backup (getAllIDBData via FLChatVault.openDump)
       * mirror.js (openIDB of conversations)

5. Migration (layer, never lose data)
   - Plain records keep working forever. Readers accept mixed plain and sealed.
   - New writes are sealed as they happen.
   - A background pass runs 3 s and 20 s after load. For each plain record:
       1) seal it
       2) open the sealed copy and compare every field with the original
       3) only if they match, compare-and-swap inside one readwrite transaction: replace only if the stored record is still exactly the plain one read
     If the app changed the record meanwhile, it's skipped (and picked up next load). A crash at any point leaves either the old plain record or the new sealed one. Both are readable.
   - Key missing (site data partly cleared, a different browser): sealed records are shown as "Locked conversation" and "Locked on this device. This was sealed with a key this browser no longer has. It has not been deleted." They are never re-sealed, rewritten or deleted. If app code writes a locked placeholder back, the original sealed blob is put back instead. A new key gets a new key ID, so new chats still work.
   - No WebCrypto (file://, plain http on a LAN address): nothing is sealed, chats stay readable exactly as before, and the Memory Vault says so.
   - Backups stay readable files so they restore on any device. That was true before; it's now said out loud in the status line.

6. What the person sees
   Settings, Memory Vault section, one line (textContent):
     "Chats sealed on this device with AES-GCM: N records sealed, N still plain (they seal on the next pass). Key ID phi-.... The key lives in this same browser, so this stops casual reading of the storage files, not someone using this browser or a compromised device. Saved backups are readable files: keep them somewhere safe."
   privacy.html: the older line "They are not locked with a password by default." stays. A Newer line follows it (exact text is in the diff). The "Every conversation is encrypted locally" row gets a short Newer note.

======================================================================
THE HONEST NOTE (say this wherever we mention it)
======================================================================
The key lives in the same browser as the chats. That protects against casual reading: someone copying the browser's storage folder, a sync or backup tool that grabs the database files, a curious glance at DevTools storage. It does NOT protect against:
  - someone who can open this browser profile (the app opens chats for them like it does for you)
  - harmful code running on the page (an extension or injected script can ask the vault to open things)
  - a compromised device
It is still not a password lock. The only mode that resists someone holding the device is a passphrase mode (see "later"). Do not write "encrypted" without "on this device, key in the same browser" next to it.
