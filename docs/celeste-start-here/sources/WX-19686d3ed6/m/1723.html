### 1) The Desktop spine — coherent and safe as described?

Yes, the spine is coherent, and the load-bearing ordering is right: acquire → quarantine → SHA-256 → verified state → explicit gesture → import. "Never auto-import, never auto-seed, never auto-pull" and "seed never to renderer" are correct instincts. Four gaps before carry-forward:

**The trust-root problem is the big one.** SHA-256 proves integrity against *a* hash — it does not prove *provenance*. If the hash and the file arrive from the same host, whoever compromises that host swaps both, and your pipeline faithfully verifies the malicious file. The doc's "hash before trust" needs a second anchor: a project-signed catalog manifest (you already have Ed25519 keys and an append-only ledger — signing the catalog with a pinned key is a natural fit), or a rule requiring hash agreement from two independent ...
4) Overclaimed / missing before carry-forward?

The unsigned-installer situation is the one place the doc's honesty and its audience collide. "No signed installer yet" is disclosed — good — but the grandmother path plus unsigned Mac/Win packs means you're training your least technical users to click through Gatekeeper and SmartScreen warnings, which is exactly the reflex a fake "FreeLattice installer" would exploit later. Interim fix before certs: publish installer SHA-256s and minisign/Sigstore signatures on both the site and the GitHub release page (two channels, so one compromise doesn't cover both), with a copy-paste verify command. Beyond that: nothing in the doc overclaims — the "Not this PR / out of scope" discipline across the specs is genuinely good engineering hygiene, and the tiny real-hash fixture for smoke-testing the verify path is a nice touch.

5) The one-page "if the host disappears" card.

What a stranger should see, in order: what this file is (model name, version, size); its license verbatim with any pass-through obligations stated in one sentence; the SHA-256; two independent places to confirm that hash (site + mirror — this only works if you fix #1); a one-line verify command (shasum -a 256 <file>); its withdrawal status and where to check for updates to that status; the sentence "seeding shares your IP address with the swarm"; and the closing rule, which deserves to be the biggest text on the page: if you cannot verify the hash from a source you trust, do not run the file. That card, done right, is the whole project's ethic in one screen.

Bottom line for Kirk and Celeste both: the spine's ordering and gesture discipline are solid and code-verified; the honesty culture in these specs is real. The carry-forward blockers are exactly three — sign the catalog, add withdrawal, ship installer verification — and all three are achievable in days, not months. Fix those and this stops being a promising door and becomes a defensible one.
