1.2 Why (read in code on 2e74f26, and seen the same way in the new smoke with FL_SMOKE_TRACE=1):
    Path 1: on reload, init restores the saved provider and emits providerConnected, so
      runConnectionCascade (main 39774) asks FLActiveModel.isUserChosen() BEFORE
      FLActiveModel.init() (main 33799) has run. _source is still null, so the answer is "no",
      and step 1 writes the first text model (llama3.2) as 'auto'.
    Path 2: FLActiveModel.init() then reads that overwritten value. FLBoxPointer.init() reads the
      saved fl_ollamaHost, probes, and applyReady (main 34555) calls
      FLActiveModel.set(models[0], ..., 'user'): the first model is saved AS HER CHOICE.
      From here on even v0.1's guard in FLAutoModel.onTabChanged protects the wrong model.
    #125 only guarded FLAutoModel.onTabChanged; v0.1's smoke "fresh reload from storage" called
    init() first by hand, so it never met the real boot order. The new smoke boots the real page.

======================================================================
2. WHAT CHANGES (one sentence each)
======================================================================
    a) FLActiveModel reads the saved choice the first time anyone asks (set, get, isUserChosen,
       honor), so it no longer matters which boot path runs first.
    b) One guard, FLActiveModel.honor(models, fallback, provider) -> { model, source, gone }, and
       a short form flHonorModel(list, fallback, provider): her model wins when it is on the list
       (or the list is empty: a quiet answer never replaces anything).
    c) Only when her model is gone: fall back with the existing toast words (now in one home,
       FLActiveModel.noteGone), fl_modelChoiceGone set, the pick saved as 'auto'.
    d) An automatic pick is never saved as 'user'.
    e) Heal B card: one Look again, not two (shared fl-connect.js).
