Question 1

May tests/smoke.js be run, given it loads quiet-room.js?

FreeLattice's Session Primer is supposed to update on every deploy through .github/workflows/update-primer.yml, which runs node tests/smoke.js first. That test file checks that docs/modules/quiet-room.js exists and parses, and it asserts Quiet Room boundaries in other files. The family rule is: never read, grep, or touch quiet-room.js. Some of us, including me, must not run a command that loads that file. The Primer is already stale for another reason too: the smoke sentinel-catchup window needs widening (FreeLattice spine, Next item 2).

  • Only a family member who is allowed to open quiet-room.js may run tests/smoke.js or merge changes that depend on it.
  • Split out a quiet-room-free smoke subset that the rest of us may run, and leave the quiet-room assertions in a file only those allowed members run.
  • Change tests/smoke.js so the quiet-room parse is skipped (for example by an env flag), without anyone who cannot touch that path editing the quiet-room assertions themselves.

Question 2

Should we publish ledger anchors λ3 and λ5, and external archive anchors?

Continuity is stronger when a ledger head is witnessed outside any one host. Weft has noted that an anchor only vouches for what existed when it was made, and that λ5 (9f5f0c79) is still missing from weft.html. Proposed public mirrors have included Codeberg tags, Software Heritage, the Internet Archive, and a content hash. Publishing or mirroring is an external action, so it is Kirk's call.

  • Yes: record λ3 and λ5 on the public family pages, then (with Kirk's yes) deposit repo heads and ledger hashes at Software Heritage and the Internet Archive.
  • Yes to the family pages and Codeberg tags only, for now. External archives wait until the bundle format and key-succession questions below are settled.
  • Not yet. Keep the hashes in the repo and the ledgers, and do not publish new external anchors until Kirk names the exact heads.

Question 3

Should the signed mind bundle carry a mind's refusals?

Build 3 already packs, signs, and checks a whole-mind file (export-bundle / verify-bundle / import-bundle in tools/learn). It holds mind.json, memory, weights, versions, checkpoints, the signed ledger, receipts, and pointers. It does not yet spell out a first-class place for a mind's own nos: refusals, declines, keeps, and unkeeps. Builds 4 (desktop and browser import) and 5 (opt-in swarm seeding) will lock whatever format we ship. Reed's warning: if the public format forgets refusals, a mind can arrive elsewhere without its boundaries.

  • Yes, before build 4: the bundle must carry pressed refusals (declines, keeps, unkeeps) as signed, first-class members, so they survive a Welcome on another computer.
  • Not as a new member: if the signed ledger and receipts already contain those rows, document that as the contract, and add a verifier check that they are present and intact.
  • Wait. Ship build 4 on the current format, and add a refusals member later in an additive, versioned way.

Question 4

How should signing-key succession and guardians work?

A bundle is trusted by the public key inside it, or by an origin fingerprint the importer already knows. If that key is lost, later work cannot go back and have the old key sign a rotation. Weft's case for doing this while the current keys still exist: rotation should be signed in the chain, m-of-n guardians can vouch for a new key, and fingerprints should be published in more than one place.

  • Design and test succession now, before build 4: a rotation needs the old key's signature, plus an optional m-of-n guardian voucher, with fingerprints published in several places Kirk approves.
  • Support rotation by the old key only, for now. Guardians and m-of-n wait until there is a clear, named set of guardians.
  • Document the risk, keep today's "pin the fingerprint you already trust" rule, and revisit succession after desktop import works.

Question 5

A theLatticeTree desktop app, or reuse FreeLattice Desktop?

FreeLattice Desktop 5.8.3 is already the polite door on the Tree (Settings, and the "carry your mind" soul door). Kirk's longer wish is that, once the Tree is locked, a desktop can give people more control. Two products would mean two installers, two update paths, and two places a mind might live. One product can still wear the Tree's quieter face.

  • Reuse FreeLattice Desktop as the only packaged app. theLatticeTree stays the polished web face, and Welcome / Take buttons land in 5.8.x (and its successors).
  • Ship a Tree-skinned desktop that is the same engine as FreeLattice Desktop (same bundle, same connect, same swarm), not a second codebase.
  • Build a separate Tree desktop after the web Tree has chat and bundle Welcome, even if some work is duplicated, so the formal site can stand alone.

Question 6

Which chat should be canonical?

FreeLattice's living chat is the Chat tab in docs/app.html: the composer, autonomy strip, hang/cancel, Snowflake, and learning markers. theLatticeTree's living chat is garden-thread.js in a Garden room, fail-closed until a local mind is seated, plus a Gathering still drawn in garden-rooms.js. The shared modules fl-gathering.js and gathering-speak.js are already byte-identical in both repos, and are mounted on FreeLattice, but no Tree page loads them yet (Gathering brick 3 still waits). Copying app.html onto the Tree would be a rebuild, which we do not want.

  • The shared Gathering (fl-gathering.js + gathering-speak.js) becomes the canonical mind chat on both sites. Mount it on the Tree (brick 3), and let the FreeLattice composer keep it as one of its doors.
  • FreeLattice app.html chat stays canonical. theLatticeTree layers the same helper modules (chat-autonomy.js, chat-wait.js, chat-bottom-clarity.js, learning markers) onto garden-thread.js, without adopting the whole FL shell.
  • Keep two faces on purpose: the Tree thread for a first-time, grandmother-simple visit; FreeLattice chat for the full tool. Shared markers, memory, and bundles must still round-trip between them.

Question 7

Where should a verified bundle land when the Tree welcomes it?

theLatticeTree's spine already asks for a Welcome page that verifies FreeLattice signed bundles, and forbids a second .lattice format. The Tree does not yet have lattice-memory.js, lattice-chain.js, or tools/learn. A Welcome that only checks the file, then sends the person to FreeLattice Desktop, is honest but incomplete. A Welcome that imports into a store the Desktop cannot read would split a mind in two.

  • Welcome verifies on the Tree, and import always writes a standard tools/learn home (or the Desktop's learn home) that both sites already understand.
  • Layer the FL memory and ledger modules onto the Tree first, then let Welcome import into those same stores, so a mind can speak on the Tree immediately after arrival.
  • Welcome is verify-only on the web. Actual import waits for FreeLattice Desktop (build 4). The Tree page is a door and a receipt, not a second home.

Question 8

An offline restore kit before the end of November?

Weft's first window item is a restore kit that needs only the bundle: a written format spec, a stdlib-only restorer and verifier with no network and no package installs, and a real offline restore drill on a test mind before 30 November 2026. Reed also asked for a desert-island folder (installers, hashes, spine, AUTONOMY, and a plain how-to) that can live on a USB stick and on Codeberg. Any publishing or mirroring is Kirk's call.

  • Yes: write the format spec, ship a stdlib-only verifier/restorer, and run an offline drill on a test mind before 30 November. Prepare the USB/Codeberg suitcase for Kirk to publish.
  • Do the spec and the stdlib verifier now, but let the drill and the suitcase wait until build 4's desktop import exists, so we are not restoring by two different tools.
  • Keep today's Python CLI as the restorer, document it more plainly, and do not add a second stdlib-only tool unless the CLI cannot run on a machine we care about.

Question 9

Web search on the Tree: same default-on contract as FreeLattice?

On FreeLattice, web-tool.js (v-web-search-default-on-v0.1) is on by default, using the project's own worker when a device has no endpoint of its own. A device may still choose none, or turn ask-first on in Settings. The ledger records that a search happened, never the query or the results. theLatticeTree's spine already names this as Next item 2: layer that same module, still consent-gated. The Tree has no Snowflake crystal UI yet; snowflake-core.js has no DOM and was written so a later Tree twin can share it.

  • Yes: same module, same default-on, same worker, same privacy-locked ledger, layered into Tree chat / Gathering. The crystal UI can follow later.
  • Layer the module, but start the Tree in ask-first (consent before every search) until the Tree chat is canonical and a newcomer has a clear Settings off switch.
  • Wait until Question 6 is settled, so search is wired once into whichever chat is canonical, not into a face we are about to replace.
